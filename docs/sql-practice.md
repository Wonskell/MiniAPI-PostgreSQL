# SQL в MiniAPI

Примеры рассчитаны на PostgreSQL. Они охватывают распространённые темы практикума; конкретная методичка курса к проекту не приложена.

## Схема и связь таблиц

Один отдел может содержать несколько пользователей. Пользователь относится к одному отделу или не имеет отдела. Связь реализована внешним ключом users.department_id → departments.id.

Название отдела хранится в departments, поэтому его не нужно изменять в каждой записи пользователя. Поле departmentName в ответе API получено через JOIN, отдельного столбца в users для него нет.

## Ограничения

- PRIMARY KEY однозначно определяет строку: UUID пользователя и числовой ID отдела.
- NOT NULL запрещает отсутствие обязательных полей.
- UNIQUE запрещает повторение названий отделов с тем же регистром.
- CHECK проверяет диапазон возраста и непустое имя независимо от того, кто пишет в БД.
- FOREIGN KEY запрещает назначать несуществующий отдел. ON DELETE SET NULL сохраняет пользователей при удалении отдела.

API проверяет данные до запроса, чтобы вернуть понятную ошибку. Ограничения базы остаются последним уровнем проверки для прямых SQL-запросов и других клиентов.

## Запросы приложения

В UserManager.cs можно сопоставить методы и темы SQL:

| Метод | SQL | Назначение |
| --- | --- | --- |
| AddUserAsync | INSERT, RETURNING, WITH | Добавить запись и вернуть её вместе с названием отдела |
| GetAllAsync | LEFT JOIN, ORDER BY | Показать в том числе пользователей без отдела |
| GetFilteredAsync | WHERE, BETWEEN | Ограничить возраст включительным диапазоном |
| FindByNameAsync | lower, LIMIT | Найти первое полное совпадение без учёта регистра |
| GetStatisticsAsync | COUNT, AVG, подзапросы | Получить статистику в одном SQL-запросе |
| GetDepartmentStatisticsAsync | LEFT JOIN, GROUP BY | Показать все отделы, включая пустые |
| DeleteAsync | DELETE | Удалить строку по ключу |
| ImportJsonAsync | BEGIN, INSERT, COMMIT | Атомарно импортировать партию записей |

В статистике отделов используется COUNT(u.id), а не COUNT(*): строка пустого отдела после LEFT JOIN существует, но пользователь в ней отсутствует. AVG игнорирует NULL; для пустого отдела средний возраст возвращается как NULL, а интерфейс показывает тире. Общая статистика включает пользователей без отдела.

## Параметры запроса

В запросах $1, $2 и другие позиции получают значения через NpgsqlParameter. Имя пользователя не вставляется в текст SQL. Например, апостроф в имени остаётся частью значения. Строки, добавляемые к SelectUsers, заданы в коде; пользователь не управляет именами столбцов или SQL-операторами.

## Транзакции

Импорт использует одно соединение и одну транзакцию. При успешной обработке всех строк выполняется COMMIT. При ошибке транзакция освобождается без фиксации и изменения откатываются. Повторный импорт пропускает совпавшие UUID через ON CONFLICT DO NOTHING.

Один INSERT или DELETE уже атомарен сам по себе; отдельная ручная транзакция для одной такой операции не нужна. Статистика считается одним запросом и видит согласованный снимок данных на момент его начала.

## Индексы

Индексы созданы для возраста, lower(name), внешнего ключа отдела и даты добавления. Они соответствуют условиям поиска, соединения и сортировки. На маленькой таблице PostgreSQL может выбрать последовательное чтение: наличие индекса не означает, что планировщик обязан его использовать. Для исследования плана используйте EXPLAIN ANALYZE на SELECT.

## Упражнения

Откройте sql/practice.sql в pgAdmin или выполните через psql. Там есть группировка с HAVING, сравнение со средним возрастом через подзапрос и изменения внутри транзакции с откатом. Для осмысленной статистики предварительно добавьте несколько пользователей разных возрастов и отделов через интерфейс.

Попробуйте самостоятельно:

1. Вывести отделы, в которых нет пользователей.
2. Найти пользователей старше среднего возраста своего отдела.
3. Показать число добавлений по дням с date_trunc.
4. Сравнить EXPLAIN ANALYZE поиска по имени с индексом lower(name) и без него в отдельной тестовой базе.
